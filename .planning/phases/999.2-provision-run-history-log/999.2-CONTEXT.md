# Phase 999.2: Provision Run History Log — Context

**Gathered:** 2026-06-17
**Status:** Ready for planning

<domain>
## Phase Boundary

After each `/setup-coolify` (provision) run, append a structured entry to `.coolify/provision-history.json` in the target repo so operators can see when the skill last ran, what it did, and what (if anything) needs follow-up.

Scope:
1. `provision.sh` writes a history entry on exit (both success and failure) via `trap EXIT`
2. `init.sh` adds `.coolify/` to `.gitignore` if not already present
3. Entry schema: timestamp, server alias, skill SHA, per-resource outcomes, overall result, issues, cleanup suggestions
4. File is cumulative, capped at 20 entries; `.coolify/` created with `mkdir -p` if absent
5. `validate`, `plan`, and `seed` do NOT write history — read-only subcommands stay read-only

</domain>

<decisions>
## Implementation Decisions

### File Placement
- Location: `.coolify/provision-history.json` in the target repo (alongside `coolify.yaml`)
- `.coolify/` is a new directory — created by `provision.sh` with `mkdir -p` on first run
- `init.sh` appends `.coolify/` to `.gitignore` if the line is absent (run state, not committed config)
- `coolify.yaml` stays at the repo root; `.coolify/` holds runtime artifacts only

### Entry Lifecycle
- Written via `trap EXIT` in `provision.sh` — captures both success (result: pass) and failure (result: fail) with exit code
- Cumulative: each run appends a new top-level array entry; existing entries are never modified
- Capped at last 20 entries — oldest entry dropped on write when limit exceeded
- No `--no-history` flag — always write; operators can delete the file manually

### Entry Schema
```json
{
  "timestamp": "2026-06-17T12:34:56Z",
  "server_alias": "vultr-stream",
  "skill_sha": "abc1234",
  "yaml_path": "./coolify.yaml",
  "result": "pass",
  "exit_code": 0,
  "duration_seconds": 42,
  "resources": {
    "project":        {"outcome": "EXISTS",  "name": "my-app"},
    "staging_app":    {"outcome": "CREATE",  "uuid": "..."},
    "production_app": {"outcome": "EXISTS",  "uuid": "..."},
    "volumes":        {"outcome": "EXISTS"},
    "doppler_tokens": {"outcome": "PATCH"},
    "dns_records":    {"outcome": "SKIP"}
  },
  "issues": [
    {"code": "MISSING_KEY", "message": "ADMIN_SECRET absent in Doppler stg config"}
  ],
  "cleanup_suggestions": [
    {"type": "stale_env_var", "key": "ADMIN_PASSWORD", "detail": "declared in coolify.yaml but not found in codebase grep scan"},
    {"type": "placeholder_value", "key": "DATABASE_URL", "detail": "value is TODO_REPLACE_BEFORE_DEPLOY in Doppler prd config"}
  ]
}
```

### Integration Scope
- `provision.sh` only — `validate`, `plan`, `seed` do NOT write history (read-only stays read-only)
- `seed.sh` does NOT write a history entry — keep history scoped to provision runs
- `init.sh` writes the `.gitignore` entry, not a history entry
- Resource outcomes harvested from existing `_done_line` tracking already in provision.sh (lines ~543)
- Issues harvested from `ERRORS` counter + captured fail messages
- Cleanup suggestions sourced from env_vars grep scan results (already computed by validate.sh, called as provision's first step)

### Claude's Discretion
- Exact implementation of `trap EXIT` and how to pass accumulated state to the handler
- Whether to use a temp file or bash variables to accumulate resource outcomes during the run
- Python3 inline script for JSON read/write (consistent with skill conventions — no jq dependency)
- Skill SHA: `git -C "$SCRIPT_DIR/.." rev-parse --short HEAD 2>/dev/null || echo "unknown"`
- Duration: capture `START_TIME=$SECONDS` at top of provision.sh, compute `$((SECONDS - START_TIME))` in trap

</decisions>

<code_context>
## Existing Code Insights

### Integration Points
- `provision.sh` completion block at lines 543–592: already tracks `_done_line` per-resource (EXISTS/CREATE/PATCH); this is the natural source for resource outcomes
- `validate.sh` called as provision's first step — env_vars grep scan results are already computed; need to surface stale/placeholder findings to the history writer
- `.coolify/validate.sh` hook already establishes the `.coolify/` directory convention in target repos
- `lib-config.py` handles all JSON/YAML — use `python3 -c` inline for JSON read/write in history writer

### Established Patterns
- `set -euo pipefail` in all scripts — `trap EXIT` must be set before any potential exit
- Python3 inline (`<<'PY'`) for structured data manipulation — no jq, no external dependencies
- Error accumulation via `ERRORS` counter + `fail()` function — capture these for the `issues` array
- `mkdir -p` already used in provision.sh for Docker volume paths — same pattern for `.coolify/`

### Key Variables Available in provision.sh
- `SERVER_ALIAS`, `COOLIFY_URL`, `DOPPLER_ACCOUNT`, `SSH_HOST` — all set after config load
- `YAML_PATH` — path to coolify.yaml (use as context in the record)
- `APP_UUIDS[]` associative array — per-env UUIDs
- `PROJECT_UUID` — Coolify project UUID
- `PLAN_MODE` — skip writing history if plan mode (read-only)

</code_context>
