## Summary

Phase 999.2 adds a `trap EXIT` history writer to `provision.sh` that appends a structured JSON record to `.coolify/provision-history.json` in the target repo. The record captures timing, server alias, per-resource outcomes (CREATE/EXISTS/PATCH/SKIP), issues from the `ERRORS` counter, and cleanup suggestions from the env_vars grep scan already computed by `validate.sh`.

The primary implementation challenge is accumulating per-resource outcomes across the per-environment loop (which runs for staging + production separately) into variables that are visible to the `trap EXIT` handler. The two viable approaches are: (1) global bash variables set as each resource section completes, or (2) a temp file written incrementally. Global bash variables are simpler and consistent with how provision.sh already works. The env_vars grep scan findings live in `validate.sh`, which provision.sh calls as a subprocess — these need a mechanism to pass results back up, either via a temp file written by validate.sh and read by provision.sh's trap, or by re-running the grep scan inline in the trap handler.

`init.sh` needs a two-line addition: after `./coolify.yaml` is written, append `.coolify/` to `.gitignore` if the entry is not already present. No template changes are needed.

**Primary recommendation:** Use bash global variables for per-resource outcome accumulation; use a temp file (written by validate.sh on request, cleaned up by provision.sh trap) to surface env_vars grep scan findings as cleanup_suggestions.

## Architecture Patterns

### Pattern 1: `trap EXIT` with `set -euo pipefail`

**What:** When `set -euo pipefail` is active, any unhandled non-zero exit causes immediate termination. A `trap HANDLER EXIT` fires on every exit — including `set -e` triggered exits, explicit `exit N`, and normal script completion. The handler receives the exit code via `$?` but ONLY if `$?` is read as the first statement in the handler function before any other command resets it.

**Critical:** The existing `_abort_notice` trap fires on EXIT (provision.sh line 57). The new history writer must REPLACE this trap or be combined with it. You cannot have two `trap ... EXIT` declarations — the second one silently overwrites the first.

**Existing trap in provision.sh (lines 49–57):**
```bash
_abort_notice() {
  local rc=$?
  if [ "$rc" -ne 0 ]; then
    echo "" >&2
    echo "ERROR: provisioning aborted (exit $rc). Coolify may be partially provisioned." >&2
    echo "Re-run /setup-coolify — provisioning is idempotent and resumes safely." >&2
  fi
}
trap _abort_notice EXIT
```

**Required change:** Replace the `_abort_notice` trap with a combined `_on_exit` handler that:
1. Captures `local rc=$?` immediately (first line)
2. Calls the `_abort_notice` body inline (or calls a renamed helper)
3. Writes history (skipped if `PLAN_MODE=true`)

```bash
_on_exit() {
  local rc=$?
  # Preserve existing abort notice behavior
  if [ "$rc" -ne 0 ]; then
    echo "" >&2
    echo "ERROR: provisioning aborted (exit $rc). Coolify may be partially provisioned." >&2
    echo "Re-run /setup-coolify — provisioning is idempotent and resumes safely." >&2
  fi
  # Write history (skipped in plan mode — read-only)
  [ "${PLAN_MODE:-false}" = "true" ] && return 0
  _write_provision_history "$rc"
}
trap _on_exit EXIT
```

**When to set:** The trap must be set BEFORE the first potential `exit` call. In provision.sh, the first exit is at line 30 (`$YAML_PATH not found`). Place `trap _on_exit EXIT` immediately after the arg-parsing block, before line 30. At that point `$YAML_PATH` may not be resolved yet — the history writer must tolerate empty `$YAML_PATH` gracefully.

**Confidence:** HIGH — verified from provision.sh source

### Pattern 2: Per-Resource Outcome Accumulation via Global Variables

**What:** Declare global outcome variables at the top of provision.sh (after `set -euo pipefail`), set them as each resource section completes. The `trap EXIT` handler reads them.

**Key finding from provision.sh audit:** The per-environment loop (lines 348–502) iterates over `ENV_LINES`. For the schema, `staging_app` and `production_app` are separate resource keys. The loop runs sequentially (staging first, then production). Separate variables per env handle this cleanly.

**Outcome variable naming convention (consistent with script's UPPER_SNAKE_CASE for config):**
```bash
# Declare at top of provision.sh (after args, before first exit)
HIST_PROJECT_OUTCOME=""      # CREATE | EXISTS
HIST_PROJECT_NAME=""
declare -A HIST_APP_OUTCOME  # indexed by env name: HIST_APP_OUTCOME[staging]=CREATE
declare -A HIST_APP_UUID
HIST_VOLUMES_OUTCOME=""      # EXISTS | CREATE (last env wins — typically idempotent)
HIST_TOKENS_OUTCOME=""       # CREATE | EXISTS (PATCH = rotate)
HIST_DNS_OUTCOME="SKIP"      # SKIP | CREATE | EXISTS | UPDATE
HIST_ISSUES=()               # accumulate as strings: "CODE: message"
HIST_CLEANUP=()              # accumulate cleanup suggestion JSON strings
```

**Setting outcomes — mapping existing echo lines to variable sets:**

| Line / block | Existing echo | Variable to set |
|---|---|---|
| Line 98–101: project CREATE | `echo " project_uuid=${PROJECT_UUID:-<would create>}"` | After `coolify_upsert_project`: `HIST_PROJECT_OUTCOME=CREATE` |
| Line 102 (project EXISTS): PROJECT_UUID already non-empty | Before CREATE check | `HIST_PROJECT_OUTCOME=EXISTS` |
| Line 397: `echo " CREATED $APP_NAME $APP_UUID"` | After create | `HIST_APP_OUTCOME[$ENV_NAME]=CREATE; HIST_APP_UUID[$ENV_NAME]=$APP_UUID` |
| Line 399: `echo " EXISTS $APP_NAME $APP_UUID"` | Already exists path | `HIST_APP_OUTCOME[$ENV_NAME]=EXISTS; HIST_APP_UUID[$ENV_NAME]=$APP_UUID` |
| Line 432: `echo " VOLUME ready: ..."` | After volume create | `HIST_VOLUMES_OUTCOME=EXISTS` (create exits 0 whether new or exists) |
| Lines 453–459: token skip path | TOKEN exists: ... skipping | `HIST_TOKENS_OUTCOME=EXISTS` |
| Lines 456–459: token create path | TOKEN created | `HIST_TOKENS_OUTCOME=CREATE` |
| Line 291 (rotate): `~ ROTATE` | `--rotate-tokens` path | `HIST_TOKENS_OUTCOME=PATCH` |
| Line 499: `echo " DNS A ..."` | After DNS upsert | `HIST_DNS_OUTCOME=CREATE` (dns_upsert_a_record is upsert — use CREATE/UPDATE based on record_id) |

**Note on volumes:** `ssh docker volume create` is idempotent — exits 0 whether creating new or existing. The outcome is always `EXISTS` from the perspective of "did it work?" The CONTEXT.md schema shows `"volumes": {"outcome": "EXISTS"}` — track as EXISTS post-success. Set to CREATE only if you distinguish first-run, but since that's complex, default to EXISTS post-success.

**Confidence:** HIGH

### Pattern 3: Surfacing validate.sh Grep Scan Findings as Cleanup Suggestions

**What:** `validate.sh` runs the env_vars grep scan (lines 236–248) and emits `warn "env_vars: $KEY declared in coolify.yaml but not found in codebase (stale?)"` and catches `MISSING:KEY:ENV (present but value is TODO_REPLACE_BEFORE_DEPLOY)` errors. These are the source for `cleanup_suggestions`.

**Problem:** `validate.sh` runs as a subprocess (`bash "$SCRIPT_DIR/validate.sh" "$YAML_PATH"` at provision.sh line 33). Its stdout/stderr is piped to the terminal. Variables set inside validate.sh are not accessible to provision.sh.

**Two options:**

**Option A — Temp file written by validate.sh (recommended):**
- If `COOLIFY_HISTORY_SUGGESTIONS` env var is set (a temp file path), validate.sh appends JSON lines to it for every `warn "env_vars: ..."` and `fail "MISSING:KEY:ENV (... TODO_REPLACE...)"` finding.
- provision.sh sets `COOLIFY_HISTORY_SUGGESTIONS=$(mktemp)` before calling validate.sh, reads the file in the trap handler, then removes it.
- Advantage: validate.sh stays self-contained; the mechanism is opt-in via env var.
- Disadvantage: small code addition to validate.sh.

**Option B — Re-run grep scan inline in provision.sh trap:**
- provision.sh trap re-runs the same grep logic against `YAML_DIR` and Doppler using `$YAML_PATH` and `$ENV_VARS`.
- Advantage: no validate.sh changes.
- Disadvantage: duplicates the grep logic; runs extra Doppler API calls at exit time; complex in a trap handler.

**Recommendation:** Option A. The temp file pattern is clean, the validate.sh change is ~10 lines, and it avoids duplicated logic.

**Temp file pattern (established in this codebase — `|| true` on cleanup):**
```bash
# provision.sh: before calling validate.sh
HIST_SUGGESTIONS_FILE=$(mktemp)
export COOLIFY_HISTORY_SUGGESTIONS="$HIST_SUGGESTIONS_FILE"

# provision.sh trap handler reads it:
_cleanup_json=$(cat "$HIST_SUGGESTIONS_FILE" 2>/dev/null || echo "")
rm -f "$HIST_SUGGESTIONS_FILE" || true
```

**validate.sh addition (inside grep scan loop and Doppler check loop):**
```bash
# env_vars grep scan — after existing warn:
warn "env_vars: $_gk declared in coolify.yaml but not found in codebase (stale?)"
if [ -n "${COOLIFY_HISTORY_SUGGESTIONS:-}" ]; then
  printf '{"type":"stale_env_var","key":"%s","detail":"declared in coolify.yaml but not found in codebase grep scan"}\n' \
    "$_gk" >> "$COOLIFY_HISTORY_SUGGESTIONS"
fi

# Doppler TODO_REPLACE check — after existing fail:
fail "MISSING:$KEY:$ENV (present but value is TODO_REPLACE_BEFORE_DEPLOY)"
if [ -n "${COOLIFY_HISTORY_SUGGESTIONS:-}" ]; then
  printf '{"type":"placeholder_value","key":"%s","detail":"value is TODO_REPLACE_BEFORE_DEPLOY in Doppler %s config"}\n' \
    "$KEY" "$ENV" >> "$COOLIFY_HISTORY_SUGGESTIONS"
fi
```

**Confidence:** HIGH (pattern is clean bash; validate.sh already uses `|| true` for non-critical paths)

### Pattern 4: Python3 Inline JSON Read/Write for History File

**What:** The history file is a JSON array. On write: read existing array (or `[]`), append new entry, trim to last 20, write back.

**Established pattern in this codebase:** All scripts use `python3 - args <<'PY' ... PY` or `python3 -c "..."` for structured data. Use the heredoc form for multi-line logic.

```bash
python3 - "$HISTORY_FILE" "$ENTRY_JSON" <<'PY'
import json, sys, os

path = sys.argv[1]
entry = json.loads(sys.argv[2])
CAP = 20

if os.path.exists(path):
    try:
        with open(path) as f:
            history = json.load(f)
        if not isinstance(history, list):
            history = []
    except (json.JSONDecodeError, IOError):
        history = []
else:
    history = []

history.append(entry)
if len(history) > CAP:
    history = history[-CAP:]

with open(path, 'w') as f:
    json.dump(history, f, indent=2)
    f.write('\n')
PY
```

**Note:** `sys.argv[2]` receives the full JSON entry string. Build the entry as a Python dict in bash using a heredoc-constructed JSON string, or pass it via a second temp file. Given the complexity of the entry (nested dicts, arrays), build it entirely in Python within the heredoc and pass individual values as positional args.

**Alternative approach (cleaner for complex entries):** Pass all scalar values as positional args, construct the dict in Python:

```bash
python3 - \
  "$HISTORY_FILE" \
  "$TIMESTAMP" "$SERVER_ALIAS" "$SKILL_SHA" "$YAML_PATH" \
  "$RESULT" "$rc" "$DURATION" \
  "$HIST_PROJECT_OUTCOME" "$HIST_PROJECT_NAME" \
  ... \
  <<'PY'
import json, sys, os
# parse args, build entry dict, append to array, trim to CAP, write
PY
```

This is the cleaner approach: all data flows through Python, no shell-side JSON escaping needed.

**Confidence:** HIGH — directly from established patterns in provision.sh, generate-workflow.sh

### Pattern 5: `init.sh` `.gitignore` Entry

**What:** After writing `./coolify.yaml`, append `.coolify/` to `.gitignore` if the entry is not already present.

**Existing `.gitignore` write pattern:** `init.sh` does not currently write to `.gitignore`. The pattern used in the broader codebase (and idiomatic bash) is:

```bash
GITIGNORE="./.gitignore"
if ! grep -qxF '.coolify/' "$GITIGNORE" 2>/dev/null; then
  printf '\n# claude-skills-deploy runtime artifacts\n.coolify/\n' >> "$GITIGNORE"
```

**`grep -qxF`** flags: `-x` requires full-line match, `-F` treats as literal string (no regex). Returns 0 if found, 1 if not. `2>/dev/null` handles missing `.gitignore` — `>>` creates the file if absent.

**Where in init.sh:** After the `echo "WROTE ./coolify.yaml"` line (line 182), before the generate-workflow section. The `.coolify/` directory is created at first provision run, not at init time, so no `mkdir -p` needed here.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| JSON array manipulation | Custom awk/sed | `python3 inline heredoc` | PyYAML/json already required; awk JSON is fragile |
| Trap + set -e interaction | Complex signal handling | Single `trap HANDLER EXIT` | EXIT trap fires for all exits including set -e triggered ones |
| ISO 8601 timestamp | Manual date math | `date -u +%Y-%m-%dT%H:%M:%SZ` | Shell built-in, zero deps |
| File locking (concurrent runs) | flock | None needed | provision.sh is invoked interactively, not concurrently |

## Common Pitfalls

### Pitfall 1: Second `trap EXIT` Silently Overwrites First
**What goes wrong:** provision.sh line 57 already has `trap _abort_notice EXIT`. Adding `trap _write_history EXIT` after it silently discards the first.
**Why it happens:** bash `trap` replaces the previous handler, no error.
**How to avoid:** Combine both into a single `_on_exit` function that does abort notice + history write. Replace the existing `trap _abort_notice EXIT` line.
**Warning signs:** Abort notice message no longer prints on failure.

### Pitfall 2: `$?` Reset by First Command in Trap Handler
**What goes wrong:** The exit code is `$?` but only at the instant the trap fires. Any command (even `echo`) resets `$?` to 0.
**Why it happens:** `$?` reflects the exit status of the last command run.
**How to avoid:** `local rc=$?` as the FIRST statement in the trap handler function, before anything else.
**Warning signs:** `result` is always `"pass"` in the history file even when provision failed.

### Pitfall 3: History Written Even When YAML_PATH Not Yet Resolved
**What:** The trap fires for `exit 1` at line 30 (`$YAML_PATH not found`). At that point `SERVER_ALIAS`, `SKILL_SHA`, etc. may not be set.
**How to avoid:** The `_write_provision_history` function must handle empty/unset variables gracefully — use `${SERVER_ALIAS:-unknown}`, `${YAML_PATH:-unknown}`, etc. For resource outcomes (all empty), write empty/SKIP entries.
**Warning signs:** `unbound variable` error in trap handler due to `set -u`.

### Pitfall 4: validate.sh Runs With `set -euo pipefail` — Temp File Must Be Created Before It Runs
**What:** If validate.sh fails (exits 1), provision.sh's `set -e` triggers the EXIT trap. The temp file for cleanup suggestions must already exist (created by provision.sh before calling validate.sh) so validate.sh can write to it.
**How to avoid:** Create `HIST_SUGGESTIONS_FILE=$(mktemp)` and `export COOLIFY_HISTORY_SUGGESTIONS` BEFORE the `bash validate.sh` call at line 33.
**Warning signs:** `append to file: No such file or directory` in validate.sh output.

### Pitfall 5: Per-Environment Loop Uses Undeclared Associative Array
**What:** `declare -A HIST_APP_OUTCOME` must be declared before the loop (line 348). If declared after `set -euo pipefail` but before the loop, it is fine. If it is inside the loop, each iteration would re-declare and lose previous values.
**How to avoid:** Declare all `HIST_*` variables immediately after the `trap _on_exit EXIT` line (near the top of the script), before the first potential exit that triggers the trap.
**Warning signs:** `HIST_APP_OUTCOME` has only one entry in the history record instead of per-env entries.

### Pitfall 6: `init.sh` Gitignore Append After File-Exists Guard
**What:** `init.sh` exits immediately if `./coolify.yaml` already exists (line 22–26). The `.gitignore` append must not run in that case — it's fine because the guard exits before the append code.
**Risk:** If init.sh is extended to be re-runnable in future, this idempotency must be preserved (the `grep -qxF` guard handles it already).
**How to avoid:** Place the `.gitignore` append after `./coolify.yaml` is written (line 182+), not at the top.

### `_write_provision_history` Skeleton

```bash
_write_provision_history() {
  local rc="${1:-1}"
  local duration=$(( SECONDS - _PROVISION_START ))
  local result="fail"; [ "$rc" -eq 0 ] && result="pass"
  local skill_sha; skill_sha=$(git -C "$SCRIPT_DIR/.." rev-parse --short HEAD 2>/dev/null || echo "unknown")
  local timestamp; timestamp=$(date -u +%Y-%m-%dT%H:%M:%SZ)
  local hist_dir; hist_dir="$(dirname "${YAML_PATH:-./coolify.yaml}")/.coolify"
  local hist_file="$hist_dir/provision-history.json"

  mkdir -p "$hist_dir" || return 0  # non-fatal: skip silently on write error

  # Read cleanup suggestions from temp file (set by validate.sh via COOLIFY_HISTORY_SUGGESTIONS)
  local suggestions_raw=""
  if [ -n "${HIST_SUGGESTIONS_FILE:-}" ] && [ -f "${HIST_SUGGESTIONS_FILE:-}" ]; then
    suggestions_raw=$(cat "$HIST_SUGGESTIONS_FILE" 2>/dev/null || echo "")
    rm -f "$HIST_SUGGESTIONS_FILE" || true
  fi

  python3 - \
    "$hist_file" \
    "$timestamp" "${SERVER_ALIAS:-unknown}" "$skill_sha" "${YAML_PATH:-unknown}" \
    "$result" "$rc" "$duration" \
    "${HIST_PROJECT_OUTCOME:-SKIP}" "${HIST_PROJECT_NAME:-unknown}" \
    "${HIST_VOLUMES_OUTCOME:-SKIP}" \
    "${HIST_TOKENS_OUTCOME:-SKIP}" \
    "${HIST_DNS_OUTCOME:-SKIP}" \
    "$suggestions_raw" \
    <<'PY'
import json, sys, os

hist_file = sys.argv[1]
timestamp, server_alias, skill_sha, yaml_path = sys.argv[2:6]
result, exit_code, duration = sys.argv[6], int(sys.argv[7]), int(sys.argv[8])
proj_outcome, proj_name = sys.argv[9], sys.argv[10]
vol_outcome, tok_outcome, dns_outcome = sys.argv[11], sys.argv[12], sys.argv[13]
suggestions_raw = sys.argv[14] if len(sys.argv) > 14 else ""

# App outcomes injected via env vars (too many for positional args across envs)
import ast
app_outcomes_json = os.environ.get('_HIST_APP_OUTCOMES', '{}')
try:
    app_outcomes = json.loads(app_outcomes_json)
except Exception:
    app_outcomes = {}

# Build resources block
resources = {
    "project": {"outcome": proj_outcome, "name": proj_name},
    "volumes": {"outcome": vol_outcome},
    "doppler_tokens": {"outcome": tok_outcome},
    "dns_records": {"outcome": dns_outcome},
}
for env_name, info in app_outcomes.items():
    resources[f"{env_name}_app"] = info

# Parse cleanup suggestions (newline-delimited JSON objects)
cleanup_suggestions = []
for line in suggestions_raw.splitlines():
    line = line.strip()
    if not line:
        continue
    try:
        cleanup_suggestions.append(json.loads(line))
    except Exception:
        pass

entry = {
    "timestamp": timestamp,
    "server_alias": server_alias,
    "skill_sha": skill_sha,
    "yaml_path": yaml_path,
    "result": result,
    "exit_code": exit_code,
    "duration_seconds": duration,
    "resources": resources,
    "issues": [],  # populated from HIST_ISSUES env var below
    "cleanup_suggestions": cleanup_suggestions,
}

issues_json = os.environ.get('_HIST_ISSUES', '[]')
try:
    entry["issues"] = json.loads(issues_json)
except Exception:
    pass

CAP = 20
if os.path.exists(hist_file):
    try:
        with open(hist_file) as f:
            history = json.load(f)
        if not isinstance(history, list):
            history = []
    except Exception:
        history = []
else:
    history = []

history.append(entry)
if len(history) > CAP:
    history = history[-CAP:]

with open(hist_file, 'w') as f:
    json.dump(history, f, indent=2)
    f.write('\n')
PY
}
```

## Open Questions

1. **HIST_ISSUES population — where do issue codes come from?**
   - What we know: validate.sh calls `fail()` which prints `"FAIL: ..."` to stderr and increments `ERRORS`. provision.sh checks validate.sh's exit code but does not capture individual fail messages.
   - What's unclear: Should issues in the history come only from validate.sh failures (which prevent provision from running), or also from mid-run failures in provision.sh itself (e.g., `exit 1` in the loop)?
   - Recommendation: For simplicity, populate `issues` only from cleanup suggestions found during validate (captured via the temp file mechanism). Mid-run failures are reflected in `result: fail` + `exit_code`. The `issues` array can start as `[]` for provision-level failures and be populated with suggestion-type issues from validate. This matches the CONTEXT.md example schema where issues show Doppler key problems — those are validate findings.

2. **Associative arrays and `declare -A` visibility in trap handlers**
   - What we know: `trap EXIT` fires in the same shell process; global variables are visible. `declare -A` in global scope works.
   - What's unclear: if `declare -A HIST_APP_OUTCOME` is declared at global scope (outside any function), it is accessible inside the trap handler function `_on_exit`. This is standard bash behavior.
   - Recommendation: Declare at global scope (after `set -euo pipefail`, before first `exit`) — confirmed safe.

3. **What if `.coolify/` `.gitignore` entry conflicts with an existing `.gitignore` line like `.coolify` (no trailing slash)?**
   - What we know: `grep -qxF '.coolify/'` does an exact full-line match. It would NOT match `.coolify` (no slash). So both entries could exist.
   - Recommendation: Check for both `'.coolify/'` and `'.coolify'`. Or just always append `.coolify/` since git interprets directory entries with trailing slash as directory-only exclusions — having both is harmless.
